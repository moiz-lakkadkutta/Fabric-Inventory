# Fabric ERP — Full-Stack Dogfood QA Campaign — 2026-09-02

**Scope:** Spun up the full local stack (Postgres + Redis + FastAPI + Vite, `main` @ `bdc7a30`, migrations at `f2_ap_payment_schema`) and dogfooded it from every angle and every user role — functional QA plus a full hostile-user security pass. Report-only: no application code was changed.

**Method:** Six parallel QA squads hammered the API (126 endpoints / 173 handlers) — security/hostile-user, money/sales/receipts (×2, independently), procure-to-pay/inventory/banking (×2, independently), manufacturing/job-work, accounting/reports — plus a manual browser pass over every frontend route. Every P0 below was **independently reproduced by the orchestrator** against the running stack with psql verification. Known-issues from `docs/review.md`, `docs/reviews/**`, and `TASKS.md` were used as a baseline to separate new bugs, confirmed-still-live known bugs, and regressions.

**Verdict in one line:** The security and double-entry *foundations are genuinely strong* — tenant isolation, authz, JWT/refresh, PII masking, and sequential GL balancing all held up under attack. The serious damage is a **systemic concurrency defect** (state-check-then-write with no row lock) that corrupts the ledger/stock/AR on three separate endpoints, plus GST/reporting correctness gaps that make the statutory outputs unfilable, and several procure-to-pay control holes.

## What held up (attacked, did not break) — do not re-litigate these

- **Cross-org isolation / IDOR:** from Org A's token, GET on 28 id-taking endpoints and PATCH/DELETE/finalize/approve/confirm/receive/post/void/issue/release/start/activate on 30 mutating endpoints against real Org B rows → **no leak, no cross-org mutation** (404/422-not-found, bodies byte-identical for other-org vs random id, so no existence leak). Covers bank-accounts, cheques, payments, manufacturing/*, admin/*, reports/*.
- **Authz:** all 173 handlers carry `require_permission` except intentionally-public/self-scoped auth routes; low-priv SALESPERSON → 403 on 17 privileged actions; self-elevation to OWNER → 403; role change instantly invalidates the access token (`pv` claim, no stale window).
- **Auth tokens:** tampered-sig / none-alg / empty-sig / garbage JWT all 401; refresh rotation works and a replayed rotated cookie → 401 revoked; MFA enrollment/gating/replay-guard correct.
- **Sequential GL integrity:** every voucher balances; TB nets to zero to the paisa across 20+ invoices/receipts/13 JVs/PI post+void; unbalanced/negative/single-line/cross-org JVs rejected; **8-way concurrent journal-voucher posting is race-free** (proving the fix pattern already exists in-repo).
- **GST core math (single-threaded):** per-line CGST/SGST/IGST split and slab whitelist correct; GSTR-1 excludes DRAFT/CANCELLED; B2CL ₹2.5L threshold exact; GSTIN masked without `pii.read`.
- **Idempotency:** same-key+different-body → 409 PAYLOAD_MISMATCH; same-key replay returns the cached response with no double execution.
- **Audit:** hash-chain valid, trigger-immutable even to the DB superuser, and `/v1/audit/verify` correctly detects a simulated tamper.

## P0 — Critical (data / money / stock corruption)

### P0-1 · Concurrency: "check status then write" with no row lock corrupts GL / stock / AR (three endpoints)
The single most important finding. `DRAFT→FINALIZED` (invoices), `receive_grn`, and receipt/FIFO allocation each read a status/balance and then mutate **without `SELECT … FOR UPDATE`** and with **no uniqueness on the resulting posting**. Two overlapping requests both see the pre-state and both commit. Reproduced by the orchestrator on all three:

- **Invoice finalize → duplicate GL vouchers.** 2 parallel finalizes (distinct idempotency keys) → both 200 FINALIZED; **3 vouchers** posted for one ₹815.85 invoice (₹2,932.37 of debits). Confirmed by 3 squads + orchestrator. AR, revenue, GST, P&L, GSTR-1, daybook, party-statement all inflated; TB still "balances" so nothing flags it.
- **GRN receive → multiplied stock.** 8 parallel receives → 4×200; **4 stock-ledger rows = 28 units for a 7-unit GRN**. Inventory valuation permanently inflated; ledger==position==report all agree on the wrong number.
- **Receipt (full payment) → double-allocation.** 2 parallel full receipts against a fresh single-invoice party → **2 allocation rows = ₹20,000 against a ₹10,000 invoice**, both reporting `unallocated:0`; ₹20,000 cash posted. Customer credited twice; the ₹10k that should be an advance vanishes. (Partial-receipt races *do* cap correctly, which is why an earlier squad mislabeled this safe — the full-payment path is broken.)

**Trigger in real life:** double-click, retry-on-timeout, two tabs, or offline-sync replay — all explicitly in scope per the architecture. **Fix pattern (already used by JV posting):** `SELECT … FOR UPDATE` on the aggregate row inside the transaction + a partial unique index (e.g. `voucher(org_id, reference_type, reference_id)` for invoice postings; equivalent guards for GRN receive and payment allocation).

### P0-2 · Voiding a partially-paid Purchase Invoice orphans the payment
`void_pi` has no `paid_amount>0` guard and does not unwind payment allocations. Pay ₹600 against a ₹1,000 PI, then void it → PI VOIDED with `paid_amount=600` still on it, the allocation row still points at the voided PI, and void reverses the **full** ₹1,000 in GL. Result: AP control ledger (2000) and API-computed supplier outstanding diverge by exactly the ₹600 orphaned cash, which is now invisible (no supplier-advance flow). Reproduced twice.

### P0-3 · MO completion fabricates phantom finished-goods stock (known MFGC-1, still live)
`POST /manufacturing/mo/{id}/complete` takes the operator-supplied `produced_qty` on faith — it checks only operation *state* and `produced_qty == planned_qty`, never the final operation's actual `qty_out` or QC-passed qty, and never that BOM materials were fully issued. Completing an MO that produced 8 of 10 (2 scrap), or passed only 3 of 5 QC, still books the full planned quantity into finished-goods stock and posts a `MANUFACTURING_COMPLETION` GL voucher at a cost derived from insufficient WIP. Reproduced twice. Corrupts inventory valuation, COGS, and downstream GST on sale. (Matches known MFGC-1 / MFG-S1; Wave G not shipped.)

### P0-4 · Junk party state → `NIL_NOT_A_SUPPLY` invoice charges GST, posts it, but GSTR-1 omits it
A party created with an invalid `state_code` ("XX", accepted — see P2s) yields invoices with `tax_type: NIL_NOT_A_SUPPLY` that **still compute GST, still post CR 2100 GST Payable**, yet appear in GSTR-1 with zero tax. Demonstrated books-vs-return divergence of exactly the invoice's GST. GST liability exists in the ledger that the return will never report. *(Precondition is the state-validation gap; borderline P0/P1 — filed as P0 because it silently desyncs books from the statutory return.)*

## P1 — High (broken core flow / wrong number a user trusts / no workaround)

**GST / compliance**
- **Non-GST firm charges GST on a document titled "Bill of Supply."** `has_gst=false` is consulted only for the PDF banner, never in the tax path. Moiz's own dogfood firm (no GSTIN) produces legally-incoherent invoices that collect CGST/SGST and a phantom GST-payable ledger. (Directly blocks dogfooding.)
- **GSTR-1 is unfilable for any multi-rate invoice.** CGST ≠ SGST (odd paisa dumped on CGST: 37.98 vs 37.97) — the portal validates equal halves; and B2B rows carry a blended per-invoice rate (e.g. "10.34%") instead of one row per rate. Every textile invoice mixing 5% fabric with 12/18% items is affected. (Tax-logic change → pair with CA.)

**Accounting / reports**
- **Dashboard sales KPIs count DRAFT invoices.** A ₹10,499 draft (never finalized) moved `sales_today`, `sales_mtd`, and `gst_collected_mtd` by exactly that amount (verified). Headline revenue and GST-collected are overstated by all outstanding drafts.
- **AR ageing is wrong two ways:** (a) backdated `as_of` deducts receipts that happened *after* the date (ageing "as of May 15" showed ₹525 vs true ₹110,775) — the FE exposes the date picker; (b) buckets age from `invoice_date`, not `due_date`, so any customer on credit terms looks delinquent immediately and contradicts the due-date-based `overdue_ar` KPI.
- **P&L COGS is wrong.** The `cogs` field is always 0 and the COGS ledger (5000) is lumped into generic EXPENSE; an inventory-adjustment gain renders as negative expenses, so `net_profit` can exceed `total_income`. Separately, the COGS voucher is dated *today* rather than the invoice date (period/FY mismatch on backdated invoices), and invoice-only sales (no delivery challan) post no COGS at all. Gross/net profit materially overstated. *(COGS_SALE vouchers do exist when stock is relieved — this is a report + timing bug, not purely a posting gap. Related to DEBT-01 WAC basis, still CA-pending.)*
- **No cancel / credit-note path for finalized sales invoices** (known REV-1). A fat-fingered finalized invoice is permanent; combined with P0-1, accidental duplicate vouchers can never be reversed in-app. Reports already branch on CANCELLED, so whenever cancel ships it MUST post a reversing voucher or status-driven reports (GSTR-1, ageing) will diverge from voucher-driven ones (TB, P&L) — divergence demonstrated.

**Procure-to-pay / inventory**
- **No 3-way match anywhere.** GRN over-receipt is unbounded and silent (110 against a PO of 100); a PI can bill 500 units against a 50-unit GRN; a PO is marked FULLY_RECEIVED off a **DRAFT** (un-received) GRN's quantities; a GRN can be received against a **CANCELLED** PO; and a GRN line accepts a `po_line_id` from a *different* PO (cross-PO contamination, item mismatch unchecked).
- **Bank reconciliation is structurally broken.** `/payments` and `/receipts` hardcode the shared control ledger (1100/1000) for BANK/UPI, but bank accounts must sit on sub-ledgers, so `preview` returns zero candidates for every real payment. Worse, `confirm` never checks the voucher's ledger against the account — it reconciled a **CASH** voucher against a bank account, and duplicate statement rows can each "reconcile" unrelated vouchers.
- **Lot traceability does not exist.** GRN `lot_number` is silently dropped; the `lot` table stays empty after receiving lot-numbered stock; `GET /lots` is empty; the FE inventory list shows "0 lots" for every SKU (82 lots exist in the demo DB but were created by seed, not the GRN path). Part-/lot-level tracking is a locked product requirement.
- **GRN receipt posts no GL** (GL only on PI post), so a mid-cycle Balance Sheet understates inventory; combined with adjustments that DO post at cost, the Inventory ledger (1300) drifts to an impossible **credit** balance.

**Manufacturing**
- **Karigar / job-work-in-MO is unreachable via the public API** (known MFG-1). `mo_service` hardcodes `executor="IN_HOUSE"`; only the demo seed script can produce a karigar operation, so the headline "job work with part-level tracking" differentiator can't be exercised on real data. (The state machine itself, where reachable, is correct.)
- **Master delete guards missing for BOM / Design / Operation-Master.** Only Routing enforces "can't delete while referenced by an active MO"; the others soft-delete unconditionally despite DB-level `ON DELETE RESTRICT`, orphaning even COMPLETED (GL-posted) MOs and 404-ing their detail screens.

**Sales / orders**
- **Delivery challan over-dispatch & cancelled-SO resurrection.** A DC can dispatch 250% of the SO's ordered qty (only stock is checked), and a DC issued against a CANCELLED SO succeeds and flips the SO back to PARTIAL_DC (illegal transition). Warehouse dispatches goods against orders the customer cancelled.

**Robustness / onboarding**
- **Numeric overflow → 500 UNKNOWN** (not 422) on: an invoice line whose qty×price exceeds NUMERIC(18,2) even when each field passes its cap; receipt amount; and PO `qty_ordered`. No partial rows leak (robustness, not corruption).
- **Login is case-sensitive on email → invited-staff lockout.** Invites lowercase the email but login matches byte-for-byte, so a teammate typing their address with any capital (exactly as shown in their invite) gets a generic `INVALID_CREDENTIALS`. First thing a trial customer hits onboarding staff.
- **Fresh signup token has `firm_id:null`** → every firm-scoped endpoint (`/reports/*`, `/receipts`, `/payments`, `/bank-reconciliation/*`) returns a confusing 403 "No active firm" until `/auth/switch-firm` is called. Login already auto-fills firm for single-firm users; signup doesn't.

## P2 — Medium (selected; full list in findings files)

- Party `state_code` accepts junk ("XX"/"ZZ") that invoices reject; GSTIN state-prefix mismatch accepted (24-GJ on an MH party); `is_export`/`is_sez` not settable so overseas/SEZ invoicing is impossible; `credit_limit` stored but never enforced anywhere; `PATCH /parties` can clear all four role flags and silently ignores `code` changes.
- A user-created ledger can **shadow a system ledger code** (two "1200" rows in the TB); duplicate ledger codes accepted under different COA groups — every code-keyed report/export becomes ambiguous, and the shadowed AR is invisible to AR reconciliation.
- `stock-summary` accepts and echoes `as_of` but always returns *today's* stock (mislabeled historical snapshot).
- Bank account linkable to an EXPENSE ledger; cheques accept negative/zero amounts; `DELETE /bank-accounts` always 422 and leaks internal migration guidance.
- Sales orders ignore GST in totals; SO requires `series` while invoices default it; double-cancel of an SO returns 200; unallocated receipt advances never auto-apply and make ageing disagree with the party statement.
- Report defaults resolve "today" in **UTC not Asia/Kolkata** (5.5-hr window of wrong-day defaults, and an FY-boundary edge on 1 Apr).
- QC `verdict` reads "PASS" even with rejects; `can-start` returns `allowed:true` for an operation whose parent MO isn't started; ITC-04 requires an explicit `firm_id` (every other report uses the JWT firm) and never emits the karigar GSTIN.
- **Frontend:** invoice-detail line AMOUNT shows the tax-inclusive total, contradicting the Subtotal on the same page (product-review #4, still open); Reports header FY label wrong ("Apr 2026 · FY 2025-26" — off by one FY and stuck on April); Party khata shows ₹0 / "No transactions" for a party with 5 real invoices (#22); **new invoices default the issue date to 30 Apr**, silently misdating documents into the wrong GST period; inventory list shows "0 lots" despite lots existing; dead report deep-links (`/reports/tb` → 404); manufacturing pipeline overdue badge wrong ("+100d" for 90 days) and applied to only one of many equally-overdue cards.

## P3 — Low (selected)

Not-found on single resources returns 422 not 404 across most master endpoints; 404/405 bypass the canonical error envelope (known ENV-1 family); PO/GRN/JWO state errors reuse `code:"INVOICE_STATE_ERROR"` ("Invoice cannot transition"); money fields accept >2dp and scientific notation (silently quantized); GST rounding mode (banker's) is consistent but undocumented; `/hsn` search param is `search` while `?q=` is silently ignored; login/forgot pages pre-fill real-looking dev credentials; placeholder screens leak internal task IDs ("Coming soon (TASK-055)"); notifications bell shows a hardcoded "3".

## Environment & process notes (not product bugs, but they bit us)

- **Backend won't boot from a plain `uvicorn`** — WeasyPrint's native libs fail to `dlopen` unless launched with `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib` (macOS). `make -C backend run` / `scripts/dev-native.sh` set it; the cookbook §1.3 manual command does not. Consider making the PDF probe a warning in dev, or documenting the env var in §1.3.
- **Signup is rate-limited to 3/hour/IP** — far too tight for onboarding a trial customer's staff or for testing; the concurrent QA squads exhausted it immediately. One squad **cleared the Redis `ratelimit:auth.signup` key** to proceed (a runtime-state change during the campaign — disclosed here for transparency; no app code or data was altered by it).
- **Cookbook §12 MFA procedure is stale** — it writes a plaintext `mfa_secret` the app can no longer decrypt (post-M1 AES-GCM), so `mfa-verify` 500s; and an undecryptable secret 500s instead of degrading to 401.
- **Demo tenant now carries QA artifacts** from the reproductions (duplicate vouchers, a double-allocated receipt, a few extra invoices). Clean with cookbook §14 (`DELETE FROM organization WHERE name LIKE 'QA %'` for the squad orgs; the demo-tenant race rows are on invoices created during verification).
- **Campaign provenance:** the harness spawned two squads in duplicate (money and procurement). This was not intentional but was valuable — the duplicates independently corroborated the top findings, and the finalize P0 is now confirmed by three separate agents plus the orchestrator's own repro.

## Suggested fix order

1. **P0-1 concurrency** — one focused change (row locks + unique posting indexes) closes the finalize, receipt, and GRN-receive corruption together. Highest impact, well-scoped, pattern already in the codebase (JV posting).
2. **P0-2 / P0-4 / P1 GST** — void-guard on paid PIs; state-code validation on parties (kills the NIL divergence); non-GST-firm tax path; CGST/SGST equal-halves + rate-wise GSTR-1 (CA-paired).
3. **P1 reports** — draft-excluded KPIs, ageing (paid-as-of + due-date basis), P&L COGS.
4. **P1 procure-to-pay** — 3-way match ceilings, GRN GL posting, lot creation, bank-recon ledger linkage.
5. **P0-3 / P1 manufacturing** — produced-qty vs QC/output reconciliation, delete guards, karigar reachability (Wave G).
6. **Onboarding P1/P2** — email case-insensitivity, signup firm auto-select, invoice default date.
