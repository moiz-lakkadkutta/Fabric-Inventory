## New findings (this pass)

### ENV-1 · Unmatched-route 404 returns raw FastAPI envelope (P2)

Hitting any path FastAPI doesn't have a route for returns:

```http
GET /this-route-does-not-exist HTTP/1.1
< 404 Not Found
< Content-Type: application/json

{"detail": "Not Found"}
```

Expected (per INT-8 contract): `{code, title, detail, status, field_errors, request_id}`.

**Why it matters:** clients written against the canonical envelope choke on the raw shape. The FE error handler probably already special-cases this, but it's a contract violation.

**Fix:** add a `404` exception handler in `app/middleware/errors.py` that converts FastAPI's built-in `HTTPException(404, "Not Found")` to the canonical envelope. Alternatively a catch-all router that emits the envelope for unknown paths.

**Scope:** ~10 lines + 1 test asserting the envelope on a known-bad route.

### GST-1 · `gstr1_section` is computed but never surfaced (P2)

`PlaceOfSupply` dataclass in `gst_service.py` has `gstr1_section: str` and the engine sets it correctly (`B2B`, `B2CL`, `B2CS`, `EXPORT`, `NIL`). But:

- The invoice INSERT does not persist it.
- The invoice response payload returns `null` for it.

```bash
$ curl … /invoices … | jq .gstr1_section
null    # should be "B2CL" or "B2CS"
```

**Why it matters:** GSTR-1 filing groups invoices by section. Without persisting/exposing the section, the future GSTR-1 export has nothing to bucket on — the engine's classification is dead code from the consumer's POV.

**Fix:** add a `gstr1_section: str | None` column to `sales_invoice` (alembic migration), populate at create time from `PlaceOfSupply.gstr1_section`, expose in both `SalesInvoiceResponse` and `SalesInvoiceListItem`. This is a natural pre-cursor to the GSTR-1 report (currently mock-only per §9.7).

**Scope:** schema migration + 1-line set in `create_draft_invoice` + 1 line in two response schemas + 2 tests (B2B, B2CL, B2CS keys round-trip).

### DOC-1 · QA manual §3.0 curl example uses outdated field names (P3)

The pre-seed snippets at lines 95–110 use:

- `party_type:"CUSTOMER"` → actual schema has flag fields (`is_customer:true`, `is_supplier:true`, …); `party_type` is rejected as an unknown field.
- `uom:"METER"` → actual schema requires `primary_uom:"METER"`.
- Both POSTs are missing the **mandatory** `code` field; the API returns 422 without it.

**Why it matters:** the next tester following this guide will get 422s on the first two curls and lose 5 minutes figuring out the actual schema.

**Fix:** update §3.0 to:

```bash
curl -s -X POST localhost:8000/parties -H "..." -d '{
  "name":"Anjali Saree Centre",
  "code":"P-001",
  "is_customer":true,
  "state_code":"MH",
  "gstin":"27ABCDE1234F1Z5"
}'

curl -s -X POST localhost:8000/items -H "..." -d '{
  "name":"Chiffon Silk",
  "code":"I-001",
  "primary_uom":"METER",
  "item_type":"FINISHED",
  "gst_rate":"5",
  "hsn_code":"5407"
}'
```

Also update §5.4 (line 189): the GL voucher today posts to `1200 / 4000 / 2100` (single GST ledger), not `2200/2300/2400`. The split into 2110/2120/2130 is **TASK-INT-13** (deferred, blocked on CA call).

**Scope:** documentation-only.

## UX observations (no code change required, recorded for future planning)

1. **Activity feed is empty for the most common day-1 user gesture: creating a party.** Today INT-15 emits `masters.party.create` and `masters.item.create` but they're not in the activity feed because they fired before the user opened the dashboard. The first time someone visits `/dashboard` with their freshly-signed-up org, they'll see "Signed up" and "Logged in" only. That's fine, but if INT-13/14 add receipt-cancel / refund flows, the feed will start telling a real story. Worth a sticky empty-state CTA: "Create your first invoice → it'll show up here."

2. **Login response auto-populates `firm_id` only when a single firm exists.** New owners always have one firm, so this is the common case. Multi-firm owners get a `firm_id: null` access token + `available_firms[]` and the FE has to call `/auth/switch-firm`. The UX inflection point is exactly when a customer adds their second firm — flag for INT-17 or later.

3. **Receipt response payload labels.** `series` + `number` are in the response but the FE has to concat them to display `RCT/2526/0001`. The list endpoint helpfully returns `allocations[].invoice_number` as the concat string. Consider exposing a top-level `voucher_display_number: "RCT/2526/0001"` on the receipt POST response too — would save a string-concat in `ReceiptCreatedToast.tsx`.

4. **Validation errors for "party not found" return 422 VALIDATION_ERROR with empty `field_errors`** instead of 404 PARTY_NOT_FOUND. The QA manual line 164 expects 404. Both are defensible (it's a body field referring to a non-existent resource) but it surprises consumers expecting REST semantics. Low priority; either change the error code or update the manual.

5. **Idempotency of `IDEMPOTENCY_KEY_REQUIRED` envelope is missing `request_id`.** Most other envelopes have it. The middleware that rejects this fires before `RequestContextMiddleware` has populated `scope["state"]`. Minor — same fix as ENV-1's positioning.
